# thinking-protocol：写作前思维协议（集成 superpowers brainstorming 三路径）

动笔前先用 10 分钟把"想做什么"想清楚，避免在错误方向上写完 4000 词。集成 obra/superpowers 的 brainstorming 三路径分类法，映射到论文场景。

## 1. 先分类（动笔前第一步）

判断当前任务的"粒度"，并**向用户明说分类**，允许被纠正：

| 路径 | 论文场景 | 需要的流程 |
|---|---|---|
| Spike（探针） | "这个方向可行吗？"——只需要答案的可行性验证 | 给出探针计划 2-3 句 → 确认 → 以最省成本方式验证 → 结论是建议不是成品 |
| Bounded（有界） | 已有明确研究问题，在既定框架内补一章/改一处 | 问清关键问题 → 在对话中给出简短设计 → **停下来等确认** → 再写 |
| Architectural（架构） | 新选题、新综述框架、重构论文结构 | 逐问澄清 → 给 2-3 个方案及取舍 → 分段展示设计逐段确认 → 写设计文档 → 再动笔 |

**判断标准**：不确定时走更重的那条；写作中发现复杂度升级，立即停下来说明并升级路径——**禁止中途降级**。

## 2. 逐问澄清（一次只问一个）

- 一次只问一个真正影响方向的问题，优先选择题（A/B/C 选项）而非开放题；
- 问的目的：目的（研究问题）、约束（篇幅/期刊/数据/时间）、成功标准（怎么算写好了）；
- 不追问细节之前，先判断任务是否过大需要拆解（如"平台 + 移动端 + 后台"式大项目要先拆子项目，每个子项目独立走设计流程）。

## 3. 先设计后动笔（不可省略的确认门）

- **任何任务，无论多"简单"，动笔前必须让用户确认意图**——简单任务只是设计短，不是没有设计。未经确认就写是最大浪费源。
- "太简单不用设计"是伪命题；"我已经理解所以直接写"是跳过确认门。
- 对论文：确认门 = 用户对"研究定位 / 大纲 / 目标期刊与词数"点头后再进写作阶段。

## 4. 给方案要有取舍

- 提出 2-3 个候选（选题方向/综述框架/章节顺序），每个附权衡；
- 先讲推荐方案与理由，再讲备选；
- 删特性（YAGNI）：从每个方案里砍掉不必要的部分，论文同理——砍掉不支撑贡献的内容。

## 5. 设计文档自检（写完后回头扫）

- **占位符**：有无 TBD / TODO / 含糊需求 → 补全；
- **内部一致性**：各节是否互相矛盾、架构是否匹配功能描述；
- **范围**：是否够聚焦，还是要再拆；
- **歧义**：有没有可被两种理解的需求 → 选一种并写明。

## 6. 与 ScholarSeed 流程的对接

- 本协议对应 paper-writing 的**阶段 0-1**（需求澄清 + 选题论证）：分类 → 逐问澄清 → 设计确认 → 才进文献与写作；
- 写设计文档时参考 `topic-selection.md` 的选题论证五维评分；确认门与 workflow 步骤 0/1（定期刊、定词数）对齐；
- 论文写作中的"审查官视角"即架构路径的 Spec self-review。
